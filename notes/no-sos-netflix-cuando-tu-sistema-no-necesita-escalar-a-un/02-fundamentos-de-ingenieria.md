# Primero escala el equipo y la ingeniería

Antes de elegir tecnología para cargas enormes, hay que hacer que el equipo pueda cambiar y desplegar el sistema sin introducir errores evitables.

- **Empieza por lo básico del flujo de desarrollo:** una estrategia de ramas coherente con el negocio, el producto y el equipo; pruebas; precommits; y CI/CD. Estas prácticas reducen errores básicos antes de que la infraestructura sea el cuello de botella. [`9:25`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=565) [`9:56`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=596)
- **No normalices cambios peligrosos y lentos.** Si un cambio tarda semanas o cualquier modificación rompe el sistema, gastar mucho en infraestructura no arregla esa capacidad de entrega. [`10:26`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=626)
- **Un equipo de cinco, ocho o diez desarrolladores que trabaja bien también es escala.** Para eso hacen falta límites claros, responsables identificados y procesos de ramas y despliegue que eviten que el equipo se estorbe. [`11:19`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=679)
- El ponente usa las estrategias de ramas como ejemplo de fundamentos sencillos que suelen ignorarse. Un servicio inestable para cinco usuarios requiere atención antes que optimizar una cifra hipotética de millones. [`11:45`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=705) [`12:10`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=730)
- Para poder crecer después, primero hay que establecer una base de ingeniería que permita hacerlo. [`9:25`](https://www.youtube.com/watch?v=nGeiH6GSIuU&t=565)
